## 2026-08-07: Fix the physical-iPhone startup allocator crash

Symbolicated the TestFlight build `202608060449` crash captured from the
connected iPhone. The main thread aborted on an invalid free in
`std::filesystem::path::operator/=`, called by
`GlobalData::BuildUserDataPathFromRegistry()` during startup. The legacy game
allocator replaced unsized global `new` and `delete`, but omitted the C++14
sized delete overloads used by modern libc++; allocations could therefore
cross incompatible allocator/deallocator paths.

Added sized scalar and array delete overloads to both game-memory backends and
made the release wrapper preserve those allocator exports when Xcode archives
the staged engine. The wrapper now regenerates its dSYM after staging and
rewriting the engine binary, and Fastlane refuses to upload an archive whose
executable and dSYM UUIDs differ. Added regression coverage for the allocator
symbols, XcodeGen archive settings, dSYM generation, UUID validation, and the
pre-upload guard.

Rebuilt the iOS engine and created an unsigned device archive. Its executable
exports the sized and unsized delete functions, and the executable and dSYM
both report UUID `9E75BBA3-332E-3562-9A5C-4C89886B81D8`. All Fastlane release
tests pass. Registered the connected iPhone through Xcode's provisioning API,
created a development profile, signed a separate
`com.aaron.generalszh.diagnostic` bundle, and installed it on LimeMoose without
replacing the TestFlight build. After unlocking the phone, the diagnostic app
launched past the former allocator crash, initialized SDL/Vulkan and the local
and archive file systems, then exited at
`loadFileDirectory('Data\\INI\\Default\\GameData')` because neither app
container contains imported retail data. No new iOS crash report was created;
the device log confirms the invalid-free startup crash is fixed.

## 2026-08-06: Add a local iOS Simulator startup workflow

Added an `ios-simulator` CMake preset, arm64 simulator vcpkg triplet, simulator
SDK-aware DXVK Meson configuration, and a runner that builds, stages local
retail Zero Hour data, installs, and launches the app on the newest available
iPhone Simulator. The runner uses OpenAL's null backend because CoreAudio's
Simulator `AURemoteIO` backend aborts on an RPC timeout.

The local reproduction confirmed that the asset-free TestFlight bundle exits
while loading `Data\\INI\\Default\\GameData`. With retail data staged, it also
exposed and fixed absolute host runpaths, duplicate SDL loading, DXVK's iOS SDL
framework lookup, and a null call when DXVK did not reuse the app's statically
linked MoltenVK loader. The tracked `dxvk-ios.patch` now carries those fork
changes, and the runner forces Meson's incremental check so local fork edits
cannot be hidden by an ExternalProject stamp.

Validated on iOS 18.5 and iOS 26.5 simulators. Both now reach successful
`Direct3DCreate8`, then stop cleanly when the simulated Metal device reports
that Vulkan 1.2 `samplerMirrorClampToEdge` is unavailable. DXVK's D3D9 backend
requires that feature, so Simulator can exercise packaging and startup but a
physical iPhone remains necessary for rendered-game validation.

## 2026-08-06: Correct iOS App Store runtime packaging

The first response to `ITMS-90426` forced a Swift anchor and copied the
backward-deployment `libswiftCore.dylib` into the app and `SwiftSupport`.
App Store Connect rejected both direct-Xcode deliveries, builds
`202608060026` and `202608060037`, with `ITMS-90429`. Inspection confirmed
that the game and every actual dependency are C, C++, or Objective-C; the
workaround was the only source of Swift in the package.

Removed the fabricated Swift dependency, `ALWAYS_EMBED_SWIFT_STANDARD_LIBRARIES`,
and the manual `swift-stdlib-tool` phase. The staging phase now packages the
DXVK, SDL, OpenAL, and GameSpy runtime binaries as signed framework bundles
and rewrites their Mach-O install names and load commands accordingly. The IPA
validator now rejects embedded compatibility Swift runtimes and loose custom
dylibs so this invalid layout cannot be uploaded again.

Verified the release configuration tests, XcodeGen staging tests, generated
project, generated shell syntax, and a fresh signed archive/export. Uploaded
build `202608060449` to App Store Connect with no `SwiftSupport/` folder and
no loose custom dylibs in the app bundle. App Store Connect finished processing
that build; the later Fastlane tester-distribution step failed because the
external beta app description is missing, so the lane now defaults to
upload-only TestFlight submission unless `GX_TESTFLIGHT_SUBMIT=true` is set.

## 2026-08-06: Fix Fastlane duplicate signing identity

Local `fastlane beta` got past the iOS 26.5 destination issue and built the
unsigned Xcode shell app, then failed during manual re-signing because
`codesign --sign` received the Match certificate common name and the login
keychain contained two identities with that same display name.

Added a Fastlane signing helper that reads the matched provisioning profile's
`DeveloperCertificates`, computes the certificate SHA-1 hash, intersects it
with `security find-identity`, and passes the resolved hash to `codesign`.
This keeps the lane tied to the exact Match profile certificate instead of an
ambiguous keychain display name. Added focused Ruby tests for the duplicate
common-name case and verified the assembled app signs and `codesign --verify
--deep` passes locally.

but did not pass the LunarG Vulkan SDK include directory. Meson could see

script for the generated cross file, and corrected the iOS quick-start to
initialize DXVK's nested header submodules recursively. Re-ran the iOS
configure, the DXVK external build, and `cmake --build build/ios-vulkan
--target z_generals -j 8`; all completed.

## 2026-08-05: Move iOS release CI to hosted macOS

Changed the manually dispatched iOS release workflow to use
`macos-latest`. The public repository can use GitHub-hosted macOS runners,
so TestFlight and App Store release jobs no longer wait for a self-hosted
runner to be online. Also aligned its vcpkg checkout with the valid,
project-declared dependency baseline after the previous malformed pin failed
to check out on the hosted runner. Pinned the consuming Matchfile to the

legacy `master` branch and could not install the stored signing identity.
Corrected the TestFlight lane's working directory too: Fastlane evaluates it
from `fastlane/`, while the CMake, XcodeGen, and packaging paths are rooted at
the repository root. Removed output pipes that previously hid CMake/Xcode
failures from the workflow.

Configured TestFlight uploads to wait for build processing and target the
existing internal tester group, `Aaron`. This keeps external distribution off
while ensuring successful CI uploads are made available to that group.
Keep the Match synchronization outside the repository-root build block so
Fastlane continues to resolve `fastlane/Matchfile` and its `main` storage
branch before CMake/XcodeGen commands run from the project root.

Added hosted-runner caches for Homebrew downloads, vcpkg setup, and C/C++
compiler objects. The first successful build populates them; subsequent builds
reuse bottles, package artifacts, and unchanged compilation outputs.

Updated the vcpkg baseline to the revision that contains the lockfile's FFmpeg
8.1.1#2 entry. The previous baseline only provided FFmpeg 7.1 and stopped CMake
before compilation began.

## 2026-08-04: Make the iOS release path non-interactive

Converted the iOS release workflow from a push-triggered TestFlight upload to
an explicit dispatch with separate TestFlight and App Store-review paths.

- Match now uses read-only signing assets from the organization store through
  a basic-auth token.
- App Store Connect uses a Base64-encoded team API key; no Apple ID session is
  required on the runner.
- TestFlight builds use the GitHub Actions run number as `CFBundleVersion`.
- App Store submission selects an already processed TestFlight build and only
  enables automatic release when explicitly requested.
- App repositories mint a short-lived, repository-scoped GitHub App token to
  clone the private Match store instead of carrying a long-lived Git token.
